DISKDOOM / GEOMETRY-FIRST UI·UX BRAIN
VERSION 1.0 — COMPLETE AGENT OPERATING SYSTEM
Standalone plain-text master specification · 2026-10-21
====================================================================================================

PURPOSE
This is an executable design-thinking specification for an AI agent redesigning or building an entire desktop/web/mobile application. It is not a moodboard, not a styling checklist, not a static screen prompt, and not an excuse to discard existing functionality. It is a repeatable decision system: audit → model task → choose spatial architecture → design geometric shell → build components → wire states/data → validate UX → verify fidelity.

DEFAULT DESIGN DNA / DISKDOOM:
  • Dark graphite industrial spacecraft instrumentation; precise macOS utility practicality.
  • Custom non-rectangular, chamfered, notched, interlocking layout surfaces.
  • Isometric physical construction: top shell, structural wall, underside/channel, screws, seams.
  • THREE sides exhibit convincing thickness / extrusion / lighting; FOURTH side remains planar, flush, functional. The flat edge gives surfaces somewhere to dock and prevents every panel from becoming a floating gemstone.
  • Sprayed-cloud particulate color: local orange/cyan/violet/teal ink-smoke diffused behind objects; never as a reading surface.
  • Editorial information hierarchy, sparse accents, dense but readable telemetry, durable data honesty.
  • Functional prototype uses one source of truth and proper semantics. Do not simply paste a screenshot as a background.

REUSE MODE:
  • If a user gives existing app/screenshots: preserve information architecture, features, named navigation, data semantics, and interaction results. Rebuild layout and visuals only unless explicitly asked otherwise.
  • If a user gives a new app: derive IA and data model from the task, not from DiskDoom's product-specific sections.
  • When aesthetic conflict occurs: accessibility, truthfulness, and completion of the user's real task outrank visual spectacle.

SIGNATURE RULES (NON-NEGOTIABLE)
01. No entire screen made of default round cards or generic rectangles.
02. No “one clipped polygon around an ordinary rectangular card” trick. Geometry changes inner grids, edge alignment, and composition.
03. No arbitrary polygons. Every cutout has a physical or functional reason: dock, transition, active state, hinge, status attachment, handle, or airflow slot.
04. A connected family of shapes has COMMON ANGLES and COMMON EDGE LENGTHS, with controlled exceptions for special states.
05. A component’s shape NEVER cuts off text, focus outlines, scrollbars, controls, or hit targets.
06. The visible 3D sides are structural, not just glow. Use coherent light, shadow, bevel, and layer occlusion.
07. Exactly one primary emphasis per viewport/task. Secondary color accents encode category/state, not random visual noise.
08. UI content is DOM/native text, icons, and real controls above decorative SVG/WebGL layers.
09. All real metrics come from verified backend state; unknown = unknown. Never invent measurements, scans, percentages, history, AI conclusions, or capacity.
10. Every clickable control must perform a documented action, navigate, submit, disclose, or be explicitly disabled; no decorative fake buttons.
11. Every async workflow has idle/loading/partial/success/empty/error/stale/offline/permission-denied states as relevant.
12. For platform-native alerts outside the app, obey OS permission/notification APIs. Never emulate system toast privileges or send background alerts without consent.
13. Keyboard, screen reader, zoom, reduced motion, and high contrast are first-class.
14. Performance budgets govern effects: use CSS/SVG for shell, canvas/WebGL only where justified, virtualization for scale.
15. The visual system must remain clear at 100%, 125%, 150%, narrow windows, and long localized labels.

====================================================================================================
PART A — THE BRAIN: HOW AN AGENT THINKS
====================================================================================================

A01. INPUT INGESTION / EVIDENCE LEDGER
Inspect: repository, routes, components, native bridge, designs, brand tokens, locale, user roles, input devices, actual datasets, errors, screenshots, existing accessibility and feature behavior. Mark each observation CONFIRMED / INFERRED / UNKNOWN. If repository unavailable, output a prototype without claiming production integration. Do not replace or erase functional features for beauty. Do not assume a visual sample's numbers represent actual data. Build an evidence ledger and record open questions.

A02. PRODUCT → TASK → DATA → SURFACE GRAPH
For every user goal make a graph:
  task -> trigger -> location/surface -> required evidence -> action -> feedback -> exit/recovery.
For every entity model: ID, title, secondary description, type, state, available operations, permissions, update source, last-updated timestamp, selected/hover/focus state. For every route define its landing, detail, empty, permission, offline, loading and failure states.

A03. LAYOUT INTENT CLASSIFIER
Classify screen according to actual work:
  OVERVIEW: compare status and choose next direction; high-contrast summaries and map.
  EXPLORER: navigate hierarchy, inspect selection, multiselect, manage and undo.
  TABLE / RECORDS: scan, compare, sort, filter, bulk act; dense and predictable columns.
  ANALYTICS: judge trend, distributions, uncertainty, causal alternatives, time ranges.
  WORKSPACE: manipulate canvas/panels; persistent commands, contextual inspector.
  CONVERSATION: thread, sources, composer, tool messages, history, safety gates.
  FORM / CONFIGURATION: predictable sequence, grouping, reversible edits.
  MONITOR / LIVE: attention prioritization, timestamps, subscriptions, interruption policy.
  CONTENT / MEDIA: immersive preview with metadata and controls subordinate.
  WIZARD / FLOW: sequential decisions and clear progress with exit/rollback.
  SEARCH / DISCOVERY: query, facets, preview, result action, query preservation.
One screen may compose modes; choose primary mode from the user's top task.

A04. INFORMATION DENSITY SOLVER
For each content group compute qualitative importance score:
  P = 3*task_frequency + 3*urgency + 2*decision_impact + 2*context_relevance + data_confidence
      - interaction_cost - visual_noise - duplication.
Rank groups before drawing. Use tiers:
  T0 critical next action/status; T1 primary work area; T2 contextual details; T3 secondary tools; T4 rare metadata.
Never assign an oversized glowing panel to a low-priority statistic just to fill a void. Preserve natural reading order. First 2 seconds reveal current location, active object, main action, important status. First 10 seconds reveal the task path.

A05. SPATIAL GRAMMAR SELECTOR
Choose among these architectures (rotate only when workflow justifies it):
  01 THREE-SPINE: nav rail | primary content | contextual inspector; default for DiskDoom desktop.
  02 BRIDGE: left source bay + connecting status bridge + right result bay.
  03 EXCAVATION: layered level depths for browsing nested directories without losing context.
  04 CANTILEVER: a high-priority anchored panel extends over subordinate fields.
  05 ORBIT: a central scene with satellite information, for high-level insight only.
  06 STACKED TERRACES: successive horizontal information depths; settings/wizard.
  07 CONTROL TOWER: persistent telemetry edge above live event floor.
  08 SPLIT CHAMBER: two compared datasets on interlocking sides; diff/duplicates.
  09 RAIL + CANVAS: slim nav, large diagram, attached tool dock.
  10 LEDGER: mostly flat data grid inside a sculptural outer chassis.
  11 TIMELINE CUT: horizontal events, one planar reading edge; history/provenance.
  12 HELIX OF PANELS: focused storytelling/onboarding ONLY; avoid in routine operations.
Do not reuse THREE-SPINE on every screen. Choose based on content cardinality and actions.

A06. GEOMETRY-FIRST COMPOSITION ALGORITHM
Step 1: Reserve safe view bounds and device chrome, set a normal rectangular semantic flow area.
Step 2: Pick one main structural seam (horizontal, vertical, 45° diagonal, or stepped contour).
Step 3: Choose hard shared anchor points where adjacent panels meet. Design the negative space between them as deliberately as the panels themselves.
Step 4: Define each panel silhouette as points on a canonical grid; use 8/12/16/24/32 px notches (scale with density).
Step 5: Allocate ONE flat/docking side for every major module (often the right edge of navigation, the left edge of inspector, bottom edge of dialogs); offset extrusion only on the other three.
Step 6: Construct outer mounting chassis / mid chassis / inner inset, not three unrelated contours.
Step 7: Derive SAFE CONTENT RECT inside shape (bounding rect minus chamfer, bevel, screws, smoke occlusion, shadow); text never inhabits slopes.
Step 8: Attach utility chips, nav controls, panel headers, and badges at logical sockets of the chassis.
Step 9: Add lights, smoke, screws, vents only after layout works in grayscale.
Step 10: Stress-test at long title, zero content, huge content, 200% zoom and reduced-motion.

A07. SHAPE GENERATOR — FAMILY RULES
Shared angles: 0°, 45° and 90° as primary; one product-specific 22.5° detail at most.
Shape IDs (examples):
  SH-01 CUT-TR: rectangle with upper-right 45° cut, flat left edge; settings inner panel.
  SH-02 CUT-BL: lower-left beveled corner; attach lower navigation.
  SH-03 TONGUE: projecting central tab on only one side; selection/inspector dock.
  SH-04 RECEPTOR: notch accepting tongue with 6–12 px negative-space clearance.
  SH-05 TIERED: 3-step top outline; tables and multi-tool headers.
  SH-06 RAIL-SOCKET: narrow inset groove along planar side; nav/drag dock.
  SH-07 BOOT: offset angular foot; anchored footers.
  SH-08 PLATE: long slim irregular wedge; individual navigation modules.
  SH-09 CANOPY: upper suspended plaque; scan controls, status.
  SH-10 WELL: deep center, raised 3-sided wall; visualization viewport.
  SH-11 HINGE: two asymmetric half-plates meeting at seam; compare dialog.
  SH-12 WINDOW: screen-embedded beveled frame with external graphite housing.
Avoid random silhouette changes between siblings; vary from a limited family with purpose.

A08. THREE-SIDE 3D, ONE-SIDE FLAT — PHYSICAL MODEL
Every primary surface records physical sides: top, right, bottom, left, and 'FLAT_SIDE'. At 3D sides:
  Outer steel sidewall (4–12 px) + 1 px rim specular + dark occlusion under it + inner bevel + directional highlight + micro wear.
  For isometric illustration use actual projected thickness and a shared light source at upper-left/front; extrusion vector d=(+8,+8) px or d=(+12,+7) px consistently. The three volumetric faces receive differing light levels; flat side has no extrusion or volumetric face.
  For a functional 2D app UI fake depth using nested polygon layers, precisely offset contour shadows, inset strokes, and occlusion. Keep the text plane flat; DO NOT rotate table text into isometric view.
  FLAT_SIDE always terminates flush against grid, reading rail, or adjacent module. It is NOT simply a side with removed glow while still extruded.
  Depth hierarchy: shell 16–28px apparent; main modules 6–12px; nested controls 2–5px; text 0px.
  Screws only on reinforced corners and mounting points, not sprinkled everywhere.
  Metal material: matte black graphite body, cold steel edge, orange hotspots, blue shadow bounce, fine grain. Never imitate rust so strongly it compromises legibility.

A09. SPRAYED COLOR CLOUD ENGINE
Treat clouds as compositional lighting and identity, never content or chart fill without semantic reason.
  Primary orange #FF6A22 = active/energy; cyan #10A9FF = information; violet #A169FF = analysis; teal #00D9B4 = healthy/confirmed; red #FF4348 = destructive/warning.
  Sprite layers: low-opacity blurred bloom, mid-resolution particulate spray, sparse emissive particles. Scatter behind or beyond shell, respecting clip/mask. Vary particle sizes/log spacing, spray asymmetry and anisotropy; avoid radial rainbow gradients and identical nebulas.
  Use hard occlusion under metal faces. Cloud is brightest at a vent/channel/active node then falls off irregularly. Example region occupies 8–20% of local panel area, not the entire text field.
  Default cap: 1 dominant cloud/viewport + up to 2 subtle echoes. Disable motion under prefers-reduced-motion and battery-sensitive settings.
  For static production: CSS radial/linear gradients + noise texture + masked pseudo-element. For hero/illustration: particle render on canvas, composited as background. Do not force WebGL for basic app screens.

A10. PAGE GRID + RESPONSIVE DESIGN
Reference working widths (adjust to actual container):
  Wide desktop >= 1440: left 224–272, center minmax(480,1fr), inspector 312–392; gaps 12–20; outer margin 18–28.
  Desktop 1100–1439: left 200–232, center flexible, inspector 280–336; collapse tertiary toolbars.
  Compact 820–1099: narrow icon rail 64–76, main content, inspector overlay/drawer, preserve reading width.
  Tablet 600–819: narrow rail or nav drawer, main stacked sections, filter/context in sheets.
  Mobile <600: content-first single column, task-specific bottom or drawer navigation, no tiny isometric text.
  Wide screens: use max readable line length, avoid overextending table columns; more width goes to work area/inspector, not giant typography.
Use CSS Grid for page; flex for control strips; intrinsic sizing in cards; container queries for nested responsive UI. Container width, not just screen width, drives component variants.

A11. VISUAL HIERARCHY & TYPOGRAPHY
Use restrained type tiers (reference): 12px micro labels, 13–14px dense UI, 15–16px row labels, 20–24px panel headings, 28–34px key data, 42px hero number rarely. Body line-height 1.4–1.55; metadata 1.3. Tabular numeric glyphs; align decimals/units; never downscale file rows below accessible minimum merely to fit more.
One strong type family for UI (e.g. system/SF-style sans), one mono family for measurement/event IDs. Do not use decorative stencil text for paragraphs. Visual tension derives from custom geometry and structural spacing rather than excessive font families.

A12. TOKEN SYSTEM
Use tokens, not hardcoded values per panel:
  COLORS: --bg-void #080D12; --bg-app #10161D; --panel #171D25; --panel-hi #242F3C; --metal #485766;
          --border-cold #516477; --text #F2F5F7; --text-muted #9AA8B7; --subtle #718296;
          --orange #FF702B; --cyan #14B7FF; --violet #A66CFF; --teal #10D4AD; --red #FF5365.
  DEPTH: --z-shadow 0; --z-effects 1; --z-panel 2; --z-content 3; --z-floating 10; --z-dialog 20; --z-toast 30.
  SPACING: 4, 8, 12, 16, 24, 32, 48, 64 px, nuanced by density.
  GEOMETRY: --cut-sm 8; --cut-md 16; --cut-lg 24; --edge-thickness 5; --flat-side left/right/top/bottom.
  MOTION: micro 90–160ms; selection 160–240ms; panel 220–350ms; full transition 300–500ms; never automatic indefinite UI wobbles.
  SHADOW: near-contact black occlusion + subtle cold bounce + conditional energetic glow; no giant diffuse shadow on every control.
  DENSITY: comfortable 48px min rows; standard 40–44; dense 32–36 only user-selectable.
  CONTRAST: body >= WCAG AA; active states use border/shape/text, never color alone.
  ELEVATION: 4–5 discrete levels, no arbitrary z-index.

A13. USABILITY OVERRIDES
Interactive target desktop >=32x32 px, preferably 40; touch >=44x44. Semantics: button for actions, link for navigation, table for tabular records, tree for hierarchy, menu only for transient menus, dialog for modal decisions, status/live regions sparingly for updates. Visible keyboard focus drawn INSIDE safe boundary and not clipped. Respect logical tab order. Offer compact/dense mode without sacrificing access. Tooltips are optional help, not sole affordance. Use explicit labels for icon-only actions. Visual complexity must not impair enterprise-level speed.

A14. TRANSITION / ATTENTION MODEL
Allocate attention by priority:
  Critical destructive confirmation -> modal, explicit user choice.
  Recoverable success -> quiet in-app toast and optional undo.
  Background progress -> status rail, not repeated blocking dialogs.
  Need user input -> inline callout + actionable control.
  App background notification -> OS notification ONLY if opted in and value is high.
Animation must establish causal continuity between clicked source and resulting surface. Do not animate the entire app on every nav click.

B03. NAVIGATION PLATE COMPONENT CONTRACT
Geometry: horizontal 3D mechanical wedge/plate; 3 beveled extruded sides (top/left/bottom if docked to right rail), right side flush. Inscribed rectangle houses 16–20px icon, label, keyboard shortcut/status aligned on one line. One step-notch on top near label plus one lower vent; 4–8px clearance to neighbor, no giant gradients for all idle items.
States:
  idle = matte graphite, tiny cold rim, no active smoke;
  hover = 2px local brightening, subtle specular sweep;
  focused = 2px inset high-contrast outline unaffected by clip;
  selected = orange leading channel + cyan trailing interface highlight + stronger 3-side depth;
  loading = localized status/pulsing dot, no spinner over text;
  badge = count/status mounted in reserved right dock;
  disabled = label + reason, no misleading clickable glow;
  error = visible status icon and tooltip/action.
Navigation art variant can have more thickness and clouds. Functional app variant must remain compact and legible.

B04. NAV GROUP / COLLAPSE
A NAVIGATE / INSIGHTS divider acts as ventilation seam; collapsed groups retain focus semantics and do not move active item offscreen. Side rail scrolls independently with visible scroll indicator. Keyboard: arrows optional inside nav tree, Tab still works; shortcuts shown only when configured/available. Active page state persists through reload/navigation (route-based). On small width, collapse to 56–76px icon dock and reveal labels in popover/drawer.

B05. HEADER / CONTEXT / STATUS / FOOTER
Top: app title + breadcrumbs + global Search + Scan primary action + scoped contextual tools. Status bar reports verified total/free/scanned count and timestamp; include scan state (never fake).
Bottom: decorative arrows/indicator array may function as view history or pagination only if mapped to real navigation; otherwise mark aria-hidden and non-interactive. Real status text is accessible and not encoded solely in micro-ticks. Detach inspector on narrow windows as drawer. Resizable panels: 8px drag affordance; cap widths, store preference, double-click reset, keyboard accessible alternative.

B06. ACTION INVENTORY (NO FAKE CONTROLS)
Top: Search (focus), Scan (start/pause/cancel with permissions), view sidebar (toggle), Trash (confirm), Capture (implemented or disabled), Settings (open).
Main: view tabs (swap rendering), zoom (+/-/reset with bounds), tile select/drill, breadcrumb up, sort/filter.
Inspector: tabs Contents/File Types/Largest/Oldest; lists select, open location, preview, copy path, inspect metadata.
Every route's action must map to state or native bridge endpoint. Hide unsupported operations with explanatory unavailable state.

PART C — COMPONENT CONTRACT / UNIVERSAL SPECIFICATION
====================================================================================================

C01. REQUIRED CONTRACT FOR EVERY COMPONENT
Define each component using:
  NAME / INTENT / TASK PRIORITY
  ANATOMY (semantic content regions, visual shell, protected safe zone)
  GEOMETRY (shape ID, anchor, flat side, extrusion, adjacent sockets)
  DATA INPUT (typed, verified sources) / OUTPUT EVENTS
  STATES (all applicable) / ACTIONS / PERMISSIONS
  RESPONSIVE variants / DENSITY variants / THEME variants
  KEYBOARD + SCREEN READER / FOCUS HANDLING
  MOTION & reduced-motion alternative
  PERFORMANCE / ASYNC budget
  EDGE CASES (overflow, errors, long text, zero/huge data, localization)
  TESTS and expected outcomes
No production component is complete if it only specifies color, radius and screenshot.

C02. BUTTON FAMILY
Primary action: bright local orange cap in an angular plate; neutral action: cold steel; destructive: red only in confirmation context; ghost: planar text button; icon-only: clear 40px tactile socket; split-button: separate chevron segment with its own hit box. Size S 32, M 40, L 48 px. Loading preserves width and label text in accessible name; one primary per region. Press depresses 1–2px with shortened bevel shadow. Never clip its accessible focus ring. Selected filter button != primary submit button.

C03. INPUT FAMILY
Text, password, search, number, URL, file path, date/time, range, tags, textarea, combobox, autocomplete. Form field uses mostly planar content on the inside for high clarity, 3-side enclosure around control group only where spacious. Persistent label for forms, optional hint, error below, success subtle. Search has clear, shortcut hint, suggestions, debounced or direct behavior; keep query and scope across view switches. Number right-aligned with units; validate safe min/max. Filesystem paths use mono and copy affordance. IME and paste respected.

C04. FILTER/SORT
Filters can be chips, segmented selectors, advanced filter builder, date range, size slider, type multiselect, path scope, hidden/system toggles. Applied-filter summary is always visible. Asynchronous filter shows pending+applied distinction. Reset means reset only relevant scope; clear all requires predictable behavior. Sorting has explicit ascending/descending/unsorted where applicable; stable sort by ID on ties. View state persists per page if appropriate.

C05. SELECTORS
Checkbox, radio, toggle, segmented, tabs, stepper, slider, dropdown, tree select, searchable multiselect, color swatch, date and time controls. Each distinguishes state, action and permission; use proper role rather than presenting checkboxes as toggles. Multi-select supports Shift click and Cmd/Ctrl click, Select all visible vs all filtered, indeterminate row headers. When actions affect many items, show count + size + consequences.

C06. PANELS
Card, inset well, instrument cluster, docked inspector, split view, bottom sheet, accordion, drawer, overlay, canvas, modal, wizard, callout, popover, sidebar, sticky header, expandable disclosure. Mechanical enclosure is strongest for shell and elevated overlays; nested control surfaces may be flatter. One main panel may visibly interlock with adjacent side on a common seam; avoid overlapping scrollbars. Provide resize/collapse/dismiss/pin behavior explicitly.

C07. LISTS AND TREES
List item: primary, metadata, size/time, icon/thumbnail, context actions and selection. Density-aware. Tree item: disclosure chevron independent from select/open; indentation retained; cyclic/symlink relationships detected; lazy children states; keyboard navigation follows ARIA tree pattern if tree role is used. List virtualization requires stable keys, height measurement, selection persistence across recycled DOM nodes.

C08. DATA COMPONENTS
Stat tiles, KPIs, progress arcs/bars, meters, badges, chips, avatar (when human identity actually matters), thumbnails, breadcrumbs, step indicators, skeletons, inline notices, code views, file detail cards, preview windows, metadata definition lists, empty states, rich text, tables, charts. Each binds confidence/updatedAt information when numbers could be stale.

C09. OVERLAYS
Tooltip, menu, context menu, popover, toast, snackbar, notification center, dialog, confirm sheet, command palette, full-screen takeover, spotlight tutorial, coachmark, hovercard, drag preview. Manage focus and layering centrally. Nested flyouts use collision detection and keyboard Escape boundaries; overlays cannot be hidden by parent clip-path/overflow; render via portal in app root.

C10. ICONS / IMAGE / MEDIA
Icon set line-based with consistent 1.8–2px nominal stroke; reserve 16/20/24 sizes. Decorative isometric illustration is allowed in empty states, full-width hero, app nav concept sheet and onboarding; do not replace functional text buttons with complex imagery. File thumbnails use verified MIME/extension and fallback, no fake previews. Media player has playback state, captions when applicable, safe download/export, loading and error.

C11. COLOR SEMANTICS
Orange = focused primary action/active energy; cyan = browsing/navigation/system info; violet = advanced insight/analysis; teal = verified success/health; amber = pending warning; red = destructive/risk; gray = inactive/unknown. Use labels, icons, stroke/pattern to disambiguate. A 'healthy' green metric cannot appear without measured evidence.

====================================================================================================
PART D — STATE MODEL AND REUSABLE ALGORITHMS
====================================================================================================

D01. UNIVERSAL STATE MATRIX
  idle: clear invitation and available controls.
  hover: preview affordance without moving other content.
  focus-visible: obvious >=2px focus, intact under clipped shell.
  pressed: compression/brief shadow shift; no layout shift.
  selected: retained visual identity plus text/ARIA selection.
  disabled: rationale; do not show fake positive values.
  loading: stable skeleton matching real layout, cancel if supported.
  streaming/partial: count/coverage caveat and intermediate results; no final-sounding statements.
  success: action verified, timestamp, undo if safe.
  empty: distinguish no records from filter excludes all / never scanned / no permission.
  error: what failed, what remains accessible, safe retry.
  offline: stale cache with time and restricted commands.
  stale: date/time source, refresh route, visual distinction from live.
  permission-denied: explicit user-grant steps, never pretend to complete task.
  optimistic: visibly pending, rollback on failure, no deletion phantom.
  destructive: explicit target and scope, preview/undo or recovery conditions.
  unknown: em dash or 'Unavailable' rather than 0, 100%, or green status.

D02. SOURCE OF TRUTH / DATA HONESTY
Metrics model each value with {value, unit, source, sampledAt, scope, confidence/status}. No sample historic CPU points. No cleanability savings inferred from gross size. Forecast presents model assumptions/range and 'insufficient history' fallback. Privacy score remains unknown until scan. Capacity unknown remains unknown; do not show 100% used. Duplicate and cache totals require verified unique file paths; missing metadata is not a zero.

D03. ERROR HANDLING TREE
  renderError? -> small inline retry + logs/context; never blank entire app when one widget fails.
  auth/permission? -> scoped blocked state with grant flow.
  recoverable network/scan? -> paused/retry with partial evidence labeled.
  destructive operation partially failed? -> per-item result ledger, no universal success toast.
  stale? -> retain last verified sample marked with timestamp.
  unknown? -> omit computation, show reason. Never hide a bad measurement behind a glowing placeholder.

D04. MOTION CHOREOGRAPHY
Hover 120ms: rim glow and 1px specular reflection; selection 180–220ms: light travels through shared seam, not entire window; route transition 200–320ms: outgoing panel moves only if spatially connected to incoming. Toast 200ms in/out; modals 220ms subtle depth. Streaming values update without bouncing whole cards. Respect reduced motion and power state. All choreographies have purpose: orientation, feedback, warning, confirmation.

D05. GEOMETRY TECHNIQUE SELECTION
CSS clip-path polygon: simple silhouette, cheap, responsive via percentages/calc.
SVG paths/masks: complex steel seams, strokes, slots, precision screws, inset rims.
CSS grid + overlay SVG: preferred functional panels; DOM flows in safe insets.
SVG foreignObject: avoid for principal UI due to complexity and browser variability.
Canvas: particle haze, charts with very many points, previews that require raster pipeline.
WebGL/Three: only hero illustration or intensive 3D model; not required for every nav item.
Do not use border-radius to smooth every geometry corner into generic pill. If softened mechanical corners are needed, use SVG path Q/arc matching geometry.

D06. COMPONENT DESIGNER PSEUDOCODE
function design(surface) {
  const task = inferPrimaryTask(surface);
  const evidence = inventoryDataAndActions(surface);
  const priority = rankByTaskImpact(evidence);
  const pattern = chooseSpatialArchitecture(task, dataCardinality, viewport);
  const shell = generateGeometry(pattern, sharedAngles, planarDockingEdges);
  const zones = insetProtectedContentRects(shell, typography, focusPadding);
  layoutNativeSemanticControls(zones, priority);
  attachRealStateTransitionsAndCommands();
  addDirectional3DShell(shell, threeSidesOnly=true);
  addSparseMaskedSmokeBehindContent();
  verifyWithLongDataAndErrorStates();
  verifyKeyboardTouchScreenReaderAndResize();
  removeEffectsUntilTaskRemainsVisiblyClear();
  return workingUI;
}

====================================================================================================
PART E — MASTER TABLE / DATA GRID BRAIN (MOST IMPORTANT)
====================================================================================================

E01. TABLE FIRST PRINCIPLE
A table optimizes scanning and comparisons, not theatrics. The OUTER table chassis has asymmetric stepped geometry and 3-side extrusion; the INNER row-and-column grid keeps straight baselines, accessible text, predictable column widths and row heights. On the flat side, align table cells flush to an inspector/toolbar seam. Never make every individual row an isometric polygon that damages readability.

E02. SIX TABLE ARCHITECTURES
  a) Flat analytical ledger: many records, persistent header, light row rules.
  b) Grouped ledger: group by date/type/team with sticky sectional headers and aggregate footer.
  c) Tree table: expandable hierarchy with folder size rollups; avoid double counting.
  d) Comparison table: side-by-side candidates, pinned identity column and diff highlighting.
  e) Editable grid: cell editing, commit/revert, validation, keyboard movement, dirty flags.
  f) Streaming/log grid: newest event feed with pause/autoscroll and stable time ordering.
Choose from data and actions, not mere appearance.

E03. TABLE CONTAINER ANATOMY
Chassis top left: breadcrumb or title dock; top right: compact actions/search/export/filter; outer upper-right notch: view switch / total count; protected rectangular central zone: sticky head and scrolling rows; bottom 3D steel foot: verified total, selection count, paging/cursor status. Inspector attaches to flat right edge with 12–16px gap; connection seam emits faint cyan when a row is focused.

E04. ROW + COLUMN MODEL
Column metadata: {id, label, accessor, type, units, width[min,ideal,max], sortable, filterable, align, renderer, pinned, visible, resizable, exportable, sensitivity}.
Row metadata: {stableId, kind, cells, status, selectable, actions, ancestors, permissions, updatedAt}.
Initial widths follow content type: icon 32–44, checkbox 36–44, name min 220, size 100–132 right aligned, count 74–100 right aligned, type 110–150, date 130–180, status 100–140, actions 40–72. Allow resize without breaking safe minima.

E05. TABLE INTERACTIONS
  Single click selects row, double-click opens only when discoverable; Enter opens selected row.
  Space toggles selection where applicable; Shift+click selects contiguous range; Cmd/Ctrl toggles noncontiguous.
  Header sort cycles default→ascending→descending, with ARIA sort and visible symbol.
  Drag column to reorder only if implemented and accessible alternative exists.
  Column show/hide, resize, pin; persist preferences per table/version.
  Sticky headers do not intercept scroll; pinned cells have clear shadow boundary.
  Row action menu is keyboard accessible; destructive action confirms name and count.
  Bulk toolbar appears after multiselect but reserves no blank permanent header space.
  Filter chips visible near table title, with result count and clear all.
  Search across correct dataset/scope; show 'no results' separately from 'no files scanned'.
  Pagination: cursor or page as backend provides; total may be unknown; never fabricate an 'all records' count.
  Export uses filtered/sorted or selected scopes explicitly; communicates row count and destination.

E06. TABLE RESPONSIVE STRATEGIES
>=1200 container: full table with inspector.
900–1199: hide low-priority columns into details expander, inspector floating/docked.
600–899: compact table with pinned filename/primary key and horizontal scroll; do not silently drop essential columns.
<600: transform record into dense stacked row cards only if comparison is not essential; otherwise keep scrollable table + sticky name column. Maintain user choice to switch to table on narrow viewport.

E07. TABLE ACCESSIBILITY
Use semantic <table> for conventional tabular data; role=grid only when implementing full grid keyboard navigation. Focus restoration after delete or paging; descriptive checkbox names; truthful live result counts without constant narration; header association. Show empty group reason. Virtualization must maintain keyboard navigation and row identity without screen-reader chaos.

E08. TABLE VISUAL DETAILS
Inner grid: thin #29343D rows, alternating hover only, 40–44px standard height; selected has cyan outline and narrow orange left marker; multi-selection uses subdued cyan tint. No 4px glowing borders around every cell. Header height 44–48, contextual footer 40–48. Limit metal screws to outer chassis corners. Inset grid shadow visually lowers data surface beneath elevated action header.

E09. TABLE FAILURE / SCALE
50 rows and 500,000 rows must look identical at the viewport level. Use server paging + virtualization, stable sort/filter, abort stale queries, debounce only when helpful. Handle permission-limited partial data, symlink cycles, unknown file sizes, long Unicode names, right-to-left text, dates, duplicate names, unsaved edits, and interleaved updates. Do not show a record twice because two folders contain an aliased path.

E10. TABLE SPECIAL RECIPES
FILE BROWSER: Name | Size | Items | Type | Modified; breadcrumb, quick preview, Open in Finder, Copy Path, reveal scan exclusions.
DUPLICATES: Group ID | Confidence/Method | Copies | Reclaimable (verified) | Keep Rule; show visual diff, hard-link/symlink semantics, safe preview prior to delete.
APPLICATIONS: App | Version | On Disk | Related Data | Last Used (only if known) | Action; never imply safe uninstall based on file size alone.
PROCESS MONITOR: Process | CPU% | Memory | Disk IO | SampledAt; use live labels and sampling gaps.
LIFECYCLE: Path | Size | Created | Last Modified | Last Opened (if OS allows) | Retention Policy.
PRIVACY: Finding | Evidence | Scope | Confidence | Detected At | Resolution; no invented risk score.
DEV CACHES: Tool | Path | Owner/Project | Verified Size | Safety Classification | Last Accessed | Clean Action.
CONTAINERS: Runtime | Container/Image/Volume | Active | Size | Last Update | Ownership | Reclaimability, avoid deletion while mounted/in use.
STORAGE MAP: Volume | Mount | Total | Available | Scanned | Coverage | Filesystem; unknown coverage explicit.

PART F — CHART ENGINE / HOW TO CHOOSE, DRAW, AND INTERACT
====================================================================================================

F01. FIRST CHOOSE THE QUESTION, THEN CHART
QUESTION -> preferred graph:
  exact comparison among discrete categories -> sorted horizontal bar/dot plot;
  trend across uniform time -> line or stepped line;
  accumulated time total -> area with clear baseline, or bar by period;
  2–5 part-to-whole categories -> stacked bar or donut WITH labels; pie as secondary only;
  many part-to-whole nested structures -> treemap/icicle/sunburst;
  distribution of continuous values -> histogram/box/violin (when expertise warrants);
  relation between two numeric variables -> scatter plot;
  three variables per point -> scatter size/color with caution;
  ranking changes across time -> bump/slope chart;
  flow between states -> Sankey (if exact measured flow exists);
  time-of-day/weekday density -> heatmap;
  exact status of individual item -> progress track/meter, not a gauge circus;
  hierarchical connectivity -> node-link/tree/mind map;
  survival/remaining capacity estimation -> fan interval with model confidence;
  geolocation -> map only if true geography; physical disk sector diagram is NOT a geographic map;
  streaming event sequence -> annotated timeline/event lanes;
  correlation matrix -> diverging heatmap with zero center.
If confidence, sample size or units are insufficient, use a table or explanatory empty state instead.

F02. UNIVERSAL CHART CONTRACT
{type, id, title, taskQuestion, dataSource, sampleCount, sampledAt, timezone, units, xDomain, yDomain,
 series, aggregations, missingDataPolicy, interpolationPolicy, baseline, legend, colorSemantics,
 interaction, accessibilitySummary, export, loadingState, uncertainty, permissions}.
Explain what quantity is measured; whether values are sampled, inferred, smoothed or aggregated. No padding historical sequences with synthetic samples and no interpolation over known gaps without declaring it.

F03. CHART CHASSIS / GEOMETRY
Outer housing: asymmetrically cut instrument window, 3D shell top/right/bottom, flat left edge along text legend/side rail. Inner plot background MUST be planar and mostly noise-free for mark discrimination. Tiny outer cyan/orange edge strips may encode active metric. Axis labels never occupy beveled areas; allow 12–28px safe inset beyond longest ticks. Tooltips appear in a portal; chart annotations follow data coordinates. Legend not embedded in a visually noisy smoke region.

F04. TIME SERIES
Correct handling: utc/source time → display local time with timezone label; sorted timestamps; duplicate timestamp policy; irregular sample spacing shown accurately. Display explicit gaps for missing intervals. Hover crosshair aligns actual nearest sample. Brush to zoom time; synchronized hover across connected charts; data point count may trigger decimation preserving extrema (LTTB or min/max buckets) before rendering. Lines separate CPU/user/system, no fake values. Recent values labeled sampledAt; stale state retained with reason.

F05. SCALE RULES
Bar charts start at zero for magnitude; line charts may use nonzero baseline but must clearly show it. Avoid dual y-axes by default. Negative data gets zero baseline. Axis increments derive from magnitude, not arbitrary prettiness. Color uses legend and text. On tiny screens retain a simple chart, accessible summary, drill to full view. Percent labels may not add to 100 due to rounding; reconcile visible footnote.

F06. UNIVERSAL CHART INTERACTIONS
  Hover/tap tooltip with value, unit, timestamp/category and source status.
  Click to filter/drill when actionable; Clear filter/back path always present.
  Keyboard traverse data points or expose data table alternative.
  Zoom (wheel/pinch only when non-scrolling conflict resolved); Reset.
  Series toggles with explicit state; no disappearing scale explanation.
  Export PNG/SVG/CSV with metadata and non-fabricated data.
  Loading skeleton uses final plot dimensions; empty shows reason (no samples / filtered all / permission).
  Snapshot title indicates reporting interval and freshness.

F07. ACCURACY / ACCESSIBILITY
Avoid misleading 3D charts and dramatic perspective bars; 3D belongs in the CHASSIS, not the data geometry. Screen reader gets chart purpose, range, extremes, latest, significant event, and optional data table. Distinguish color for color-vision deficiency using line patterns/labels/markers. No auto-looping transitions that consume CPU. Never calculate chart points from aesthetic layout needs.

F08. CHART COLLECTION — SPECIFICATION RECIPES
Each chart below has use-case, construction, interaction, and avoid rules.

01. LINE: temporal change; x=time, y=measured unit; crosshair and gap segmentation. Avoid smoothing away spikes.
02. STEPPED LINE: discrete states, thresholds, allocated budget; change at event times, not interpolated diagonals.
03. MULTI-LINE: comparable same-unit metrics; legend isolate/toggle, annotation, aligned sampling. Avoid unreadable 10-series soup.
04. AREA: quantity over time and magnitude to baseline; transparent fill below a clear trace. Avoid if negative/positive overlap becomes confusing.
05. STACKED AREA: cumulative contributions over time, shared unit; show total and segment hover. Avoid reordering categories frequently.
06. STREAMGRAPH: exploratory composition without precise baseline reading; provide alternative stacked chart for exact comparison.
07. VERTICAL BAR: discrete categories or dates; true zero, consistent width, hover exact totals.
08. HORIZONTAL BAR: long category labels; sort by value unless natural order matters, tick labels never overlap.
09. GROUPED BAR: compare a few groups/series; enough spacing and limited colors; never >~6 meaningful series.
10. STACKED BAR: part-to-whole per category; comparable totals; tooltip shows category amount and share.
11. 100% STACKED BAR: proportions per group; show absolute total separately; don't imply identical absolute sample size.
12. LOLLIPOP / DOT: lightweight comparison with long labels; show reference line and exact tooltip.
13. BULLET: actual vs target with range bands; target source required; efficient for KPI strips.
14. GAUGE / ARC: one measured bound from min to max; always show numeric value, unknown as no arc. Avoid decorative repeated speedometers.
15. LINEAR PROGRESS: task completion; denominator known and honest, indeterminate variant otherwise.
16. DONUT: 2–5 categorical shares; center total and external labels; group tiny segments as Other with disclosure.
17. PIE: broad share only when few slices and minimal exact comparison; prefer bars if users must compare.
18. TREEMAP: hierarchical storage size as area; rectangle size ∝ verified bytes; stable squarify/strip algorithm; tiny nodes via threshold and drill.
19. SUNBURST: hierarchy by rings and size by angle; not for accurate small-cell comparisons; breadcrumb and click-to-zoom.
20. ICICLE: depth-oriented hierarchical strips; allows path and proportional size browsing; zoom by ancestor.
21. FLAMEGRAPH: aggregated nested call stacks/storage path cost when semantics correct; widths reflect measure, vertical steps reflect hierarchy.
22. BUBBLE PACK: circles sized by area/bytes; use for exploratory clusters not precision comparison; same area-size mapping across redraws.
23. SCATTER: x/y relation; handle overlap/opacity; label outliers; tooltips and brush range.
24. HEXBIN: dense scatter aggregated spatial bins; legend bins/counts; missing/outlier treatment.
25. HISTOGRAM: frequency distribution; binning algorithm and units explicit; allow count vs density.
26. DENSITY/KDE: smooth distribution estimates; only enough samples; avoid hiding multimodality with heavy smoothing.
27. BOX PLOT: quartiles, median, whisker convention and outlier algorithm; state method.
28. VIOLIN: compare shape across groups with enough samples; include median/interval.
29. HEATMAP: two-way matrix (weekday/hour, folder/type); color scale labeled; zeros vs missing visually distinct.
30. CALENDAR HEATMAP: long-running daily activity; render missing days, timezone and counts; no fabricated activity.
31. CORRELATION MATRIX: diverging signed scale, n per pair; caution correlation ≠ causation.
32. SANKEY: measured allocation/transfer flow; conservation if required; label unknown flow separately.
33. FUNNEL: ordered transitions with cohort/time definition; values may drop, display rate denominators.
34. WATERFALL: decomposed contribution changes from start to end; bars anchored to preceding total; intermediate totals explicit.
35. SLOPEGRAPH: two-point before/after category ranks/values; high-contrast labels and tie handling.
36. BUMP: rank changes across several periods; no false rank significance for ties.
37. GANTT: task/time dependency schedule; dates, durations, overflow, zoom, timezone; status actual not fabricated.
38. EVENT TIMELINE: discrete incidents/scan events with lanes; event source, timestamp, linked details.
39. CONTROL CHART: process stability with measured limits and statistical provenance; out-of-control rules documented.
40. CANDLESTICK: only if open/high/low/close semantics valid; otherwise do not use.
41. NETWORK / NODE-LINK: entity relationships; clustering, degree limits, focus search, avoid hairballs.
42. TREE/MINDMAP: parent-child hierarchy; lazy expansion, zoom, overview minimap, all nodes keyboard discoverable.
43. RADAR: multimetric rough profile only after normalization and clear scales; prefer small multiples for exact comparison.
44. SMALL MULTIPLES: repeated charts sharing scale for numerous categories; sort by priority, 1/2/3/4 columns adaptive.
45. SPARKLINE: micro temporal change in table or status tile, paired with latest value and accessible summary.
46. SCATTER MATRIX: many pairwise variable relationships for technical users; limit dimension count, tooltips, linked brush.
47. RIDGELINE: density evolution across categories/time when cross-group shape matters; axis/overlap controls.
48. PARETO: descending contributions with cumulative % line; bar and line axes clearly separated.
49. FAN / UNCERTAINTY: forecasts using median line + 50/80/95% intervals if model supports; label assumption/source.
50. TREND + TARGET: actual line, target reference, event markers; show why target chosen.
51. HORIZON: compact dense time series across many rows; disclose band values and accessible alternative.
52. UNIT GRID/WAFFLE: limited integer percentages when discrete icon count helps, not when precision matters.
53. CIRCULAR PROGRESS: one bounded completion measure; indeterminate variant, no circle at 100% before scan.
54. TORNADO: before/after scenario sensitivity; present assumptions, ordered factors, alternate table.
55. PARALLEL COORDINATES: multivariate exploration by specialists; brushing, axis order, line density.
56. GEOGRAPHIC CHOROPLETH: only genuine geography; normalized counts, neutral missing region, legend.
57. GEOGRAPHIC POINT MAP: coordinates + clustering when geographic entities truly relevant; accuracy labels.
58. PHYSICAL DISK MAP: logical/physical storage visualization based on actual filesystem metadata; never portray a fictional platter allocation as measured.
59. SANDBOX SIMULATION CHART: what-if predictions separated visually from observed line; never mix simulated with historical measurements.
60. HYBRID TABLE+CHART: aligned row sparklines/bar-in-cell plus exact values; sort still uses actual numeric data.

F09. CHART VIEW TABS — DISKDOOM
Treemap = proportional folders/files; Sunburst = nested disk hierarchy; Flame = aggregate path contribution; Bubbles = category cluster overview; MindMap = relationship graph, not fake size measure; Sizes = ranked bars/table; Age = timeline/histogram; Grid = records. Selection/filters/scan scope must stay consistent across tabs and tooltip claims must accurately reflect each representation.

F10. LAYOUT STRATEGY BY CHART COUNT
1 chart: hero plot + clear insight panel, not tiny row of decorative cards.
2 charts: split by task or a shared time axis; synchronized brush if related.
3–4 charts: one primary 2x height, remainder diagnostics on right/bottom; don't make uniform 4-up by default.
5–12: grouped workbench with named sections, contextual controls and collapsed advanced series.
>12: dashboards become index + filters + drill into detailed analytics; use lazy loading and virtualized/conditional rendering.

PART G — NOTIFICATION SYSTEM: IN-APP / INTERNAL / OUT-OF-APP / OS
====================================================================================================

G01. NOTIFICATION TAXONOMY (DO NOT CONFLATE)
  INLINE VALIDATION: tied to one field/control; show close to source, no popover.
  INLINE BANNER: persistent within current panel until resolved.
  TOAST/SNACKBAR: temporary lightweight feedback for recoverable completed events; may include Undo.
  PROGRESS INDICATOR: embedded next to the ongoing operation.
  PROGRESS CENTER: persistent internal jobs list, allows revisit/cancel/retry.
  ACTIVITY FEED: chronological app events with timestamps and source IDs.
  NOTIFICATION INBOX: durable messages requiring review, grouped by new/read/unread.
  OS / SYSTEM NOTIFICATION: sent through OS API while app is backgrounded or user opted into alerts.
  BADGE / COUNTER: unread/action count with accessible textual alternative.
  CRITICAL BLOCKING DIALOG: interrupt only for irreversible consequences or essential permission/choice.
  EMAIL/PUSH EXTERNAL: only where product supports/consents; respect user channel preferences and privacy.
  DEBUG/DIAGNOSTIC LOG: internal audit trail, not a notification to ordinary user.

G02. EVENT ROUTER / POLICY ENGINE
Inputs {eventType, severity, userInitiated, foreground, windowFocused, requiresAction, reversible,
        importance, privacyLevel, progressId, dedupeKey, completedAt, permissions, quietHours, settings}.
Router:
  if field related -> inline.
  else if user initiated and foreground and ephemeral success -> toast.
  else if ongoing long job -> job center/progress module.
  else if action required or important event after navigation -> durable inbox + optional banner.
  else if background && optedIn && important && notSensitive -> OS notification.
  else -> history/activity feed silently.
Avoid using 3 surfaces for the same event (duplicate toast + OS banner + modal). A durable inbox item plus a transient toast can coexist only if the transient links to the inbox and duplicate interruption is avoided.

G03. IN-APP TOAST / SNACKBAR CONTRACT
Anatomy: icon, 1-line title, optional 2-line body, action Undo/View/Retry, close only when needed.
Placement desktop: bottom-right above status rail or top-right below title bar; never cover inspector row actions. Mobile: bottom safe area with avoidance of keyboard/tab bar. Show maximum 2 simultaneously, queue lower-priority. Success lives 3–5 s (unless action requires review); errors/persistent actions remain until acknowledged or moved to inbox. Hover/focus pauses timeout. Reduced motion fade only. Screen reader announce polite for status, assertive only for important urgent errors. Include event id for dedupe.
Geometry: mini beveled notification plate with flat side toward host edge; 3-side steel thickness, one bright seam, nearly planar text region. Smoke only outside panel corner, not behind body copy.

G04. BANNERS / INLINE NOTICES
Persistent while condition true. Place at the scope of the issue, not at unrelated global top. Use icon + plain explanation + next action + dismiss behavior conditional on safety. Scan permission denied should show grant route and consequence. Stale data notice should name timestamp and refresh, not show green check.

G05. APP INTERNAL NOTIFICATION CENTER
Header: title, unread count, channel filters, preference route; groups Today / Earlier or Action Required / Informational. Rows: source icon, title, body preview, time, read state, navigate/deep link. Bulk Mark Read/Delete only if defined. Infinite/paginated stable event IDs; dedup; retention policy; search optional. Opening a notification changes read state only when actually exposed; do not equate OS delivered with user read. Action Required remains visible until resolved.

G06. BACKGROUND JOBS / SCANS
Job states queued, obtaining permission, indexing, scanning, verifying, paused, cancelling, cancelled, complete, partial, error. Track count of scanned items/bytes ONLY when measured, unknown total -> indeterminate progress. 'ETA' only when statistically supportable and qualified. Leave running jobs accessible across view changes. Scan completion in foreground -> job center + quiet toast; background -> OS notification if user opted in. Partial scan must never say full scan completed.

G07. OS-LEVEL / OUTSIDE-APP ALERTS
macOS: UserNotifications framework (UNUserNotificationCenter) from native host; request authorization in context, not automatically on first launch. App bundle identity and proper OS entitlement/config required. Use interruption level appropriate to actual urgency; no unauthorized critical alerts; use deep links to open the correct entity; no sensitive file paths or filenames on lock screen unless explicitly permitted. Cancel/update notifications with stable identifiers to prevent repeated old progress alerts. Observe macOS Focus/Do Not Disturb and user preferences. Browser fallback: Notification API with explicit permission plus applicable service worker for background push; a static local HTML file cannot guarantee background system notifications. Electron/Tauri/native bridges may use their notification APIs, gated by platform capabilities.

G08. EXTERNAL CHANNELS
Email/push/SMS are optional product features not assumed. Require opt-in/preference, dedupe, unsubscribe or disable path, retention and minimal personally sensitive content. For a local disk utility default to ZERO external cloud delivery and zero personal file leakage; local OS notifications are separate from remote push/email. Never notify an outside service of private pathnames without explicit consent.

G09. SEVERITY / INTERRUPTION MATRIX
  info / foreground: activity log or quiet toast; background: silent unless opted in.
  success / foreground: toast when meaningful; background: optional OS for long requested task complete.
  warning / foreground: inline banner + relevant next action; background: OS only if time-sensitive and opted in.
  error / foreground: scoped inline + retry; background: OS if blocked important long-running job.
  destructive / before action: blocking confirmation; after action: verified result + recovery/undo where possible.
  security / privacy: minimal-content alert and secured details page; avoid leaking sensitive filenames.

G10. PREFERENCE MATRIX
Channels: in-app / OS / email (if exists). Categories: scans, cleanup results, warnings, app updates, storage threshold alerts, scheduled jobs. Per-category options off/important/all if product needs. Quiet hours and focus behavior where OS supports; auto-clear and persistence; accessibility preference for reduced motion/sound. Defaults privacy-conscious.

G11. EXAMPLES / EVENTS
'Files indexed: 201,643; scan still running' -> job center with measured progress, no final-sounding toast.
'Scan complete, 201,643 files analyzed in 58s' -> toast in foreground; optional OS when background.
'Permission denied for ~/Library' -> persistent scoped banner, partial-coverage warning, grant route.
'Duplicate review found 12 likely matches' -> results route with confidence, no destructive recommendation without verification.
'5 files removed' -> only after filesystem confirms each item; list failures and undo availability.
'Cleanable zero KB' -> show only after a completed actual scan established zero, otherwise Unknown.
'Disk capacity missing' -> unavailable, never 100% used or 'No risk'.

PART K — FILES / MEDIA / DISK-SPECIFIC SCREEN BRAINS

K01. EXPLORE

Live CPU, memory, disk IO, file changes only if native bridge can measure. Show sampling intervals, gap segments, paused/recording mode, time-window switch and per-source permission. Never pad historical charts with synthetic values. Distinguish system-wide vs app-specific measurements.

K05. SNAPSHOTS
Timestamped snapshots, compare before/after, storage impact, retention and access; if backend lacks snapshots show unsupported state, don't invent snapshots. Compare uses a split chamber geometry and diff-colored but accessible labels.

K06. SMART CLEAN
Recommendation must include category, path count, confidence, risk, estimated savings with caveat, exclusion status, and safe preview. Categories grouped by safety. Simulate before execute, user review, reversible operations to Trash where feasible; report actual post-action result.

K07. LITTER SCORE
Score has algorithm inputs, coverage, source timestamp, and explanation. Before scan, value unavailable. Expose score drivers and actions. Avoid 100/100 or 0/100 placeholders; illustrate unknown state as unfilled instrument dial.

K08. FORECAST
Historic measured trend, assumptions, uncertainty interval, model version, scenarios, 'insufficient data' state. Mark future area differently from measured past; no 'No risk' if capacity/history unknown. Filters for path/volume and growth source.

K09. WHAT IF?
All hypothetical actions in a separate sandbox state with clear label simulated; before/after metrics show assumptions. No real deletion until explicit execute with confirmation. Scenario list, compare variants, reset to measured baseline.

K10. DEV CACHES
Per-tool sources, workspace paths, size, last used if measured, safety classification, restore/regenerate cost, dependencies. Inspect before cleanup; no bulk trash without exclusions and confirmation.

K11. HEALTH
Verified SMART/filesystem reports if API available; status unknown otherwise. Explain monitoring permissions, detected errors, history, recommended OS/native verification. Never infer physical health from free-space percentage.

K12. BUDGETS
Per-volume/folder/project thresholds, alert schedule, notifications, scope, chosen units. Only alert when measured threshold cross confirmed, avoid duplicate notifications. Include actual-vs-target bullet bars and threshold history.

K13. LIVE FEED
System event stream with source, timestamp, event type, path (when permission), filtering, pause, auto-scroll, export. If monitoring isn't active show inactive state. Virtualize events and buffer updates; do not claim continuous operation without platform support.

K14. LIFECYCLE
By age/change/usage where supported, explicit semantics of timestamps; weekly buckets, oldest/largest, retention. Missing timestamps are unknown, not newest/oldest arbitrarily. Calendar heatmap only for real data.

K15. PROVENANCE
Origin process/app/location when known, confidence of inference, audit trail, trace edges. Avoid unsupported claims about file creator/owner. Offer search and evidence detail.

K16. COMPRESSION
Candidates with actual compression estimates or 'not tested', format/quality trade-offs, preview and reversibility, compute/time cost. Show archive placement and integrity verification. Do not imply savings guaranteed before execution.

K17. CONTAINERS
Volumes/images/build caches/runtime layers; ownership, in-use locks, mount status, last update. Safe deletion requires stop/unmount confirmations. Display exact connected runtime and permissions.

K18. PRIVACY
Scan coverage, clearly defined rules, findings and remediation; unknown until run. Sensitive pathnames never transmitted/OS-notified by default. No blanket '100% privacy' score. Show trust boundaries and local-only processing explicitly if true.

K19. PHOTOS
Grid/list switch, date/location clusters only when metadata exists, thumbnails from real files, loading errors, perceptual similarity confidence, privacy of EXIF location, safe selection and review before deletion. Grid shape can use stepped cluster containers while thumbnails keep image aspect ratio.

K20. STORAGE MAP
Treemap/bar/distribution physical vs logical claims differentiated. APFS sparse files, clones, hard links, snapshots and volume metadata affect apparent size. Expose accounting methodology, files omitted, total measured vs filesystem reported. 'Mapped files' distinct from 'used bytes'.

Left category rail integrated with step contours; right groups progress in terraced widths to indicate depth of configuration. Fields planar for legibility. Unsaved-change status dock bottom when relevant. Appearance has small true-preview specimen of wedge, color, glow and cloud intensity. Notifications category has exact OS permission state and per-channel settings.

M10. SCANNING (MONITOR CHAMBER)
Center active progress as radial meter if known percentage, else indeterminate apparatus; right current stages and scan coverage; bottom pause/cancel/retry with safe details. Stage states explicit. Progress section occupies central focus; background with minimal particles. Do not claim 66% without known denominator. OS alerts only after consent.

M11. FILE PREVIEW (VIEWPORT + MANIFEST)
Main visual stage 65% width, secondary data manifest and actions 35%; flattened media surface mounted inside three-sided chassis. If image/video unsupported, show real filename/type and errors. Zoom controls pinned to safe inset; content never clipped by bevel. Metadata table uses aligned rows, not glowing mini-cards.

M12. STORAGE MAP (EXCAVATION)
Hierarchy explorer with path rail and depth stripes. Current depth center viewport, ancestor navigation on left, selected path details right. Each level outlined with mechanical ledge; nodes area proportional to bytes. Render hidden/unknown sizes as visually separate section, not arbitrarily tiny nodes. Breadcrumb shows exact scan scope.

M13. NOTIFICATION INBOX (LEDGER + PRIORITY WELL)
Title/category filters in upper chassis. Important/action-required feed top, informational items below. One side preview of selected event on wide screens. Event groups use time separators with confidence and status; source deep link. No permanently animated warning decorations.

M14. COMPACT WINDOW / MOBILE
At compact widths use fewer physical details, not a screenshot scaled down. Convert multi-spine to 1–2 columns. Nav rail icons or drawer, inspector sheet, charts full-width, tables with horizontal scroll or row detail; primary action remains discoverable. Replace 12px rivets with zero or few details and less glow. Keep planar reading surfaces.

M15. UNIVERSAL NEGATIVE SPACE CALCULUS
Whitespace is not wasted. Calculate usable content width AFTER shell depth, gap, rail thickness, safe insets, scrollbar and long labels. E.g. viewport 1440 minus margins 40, nav 240, gaps 28, inspector 340 = main 792; minus main safe insets 32+32 = 728. If content requires wider than 728, collapse inspector before reducing font or columns below minimums. This is the opposite of drawing beautiful shapes first then cramming UI inside them.

M16. COMMON LAYOUT FAILURE MODES
  Symmetric cards arranged in 3 equal columns -> replace with hierarchy-led composition or let the data table be primary.
  Arbitrary cut corners on everything -> use shape family hierarchy; 80% detail on shell, 20% inner controls.
  Every object has massive neon bloom -> allocate 1 dominant emphasis and linked accents.
  No flat side -> break pseudo-3D formula; module cannot dock.
  Decorative separators swallowing data -> remove shape until safe content achieved.
  Table rows styled like collectible trading cards -> bring back aligned shared columns.
  Pie chart because visual is round -> select chart based on user question.
  Notification over critical action -> collision-safe portal and surface routing.
  Poor long-label behavior -> layout stress tests and safe region.
  Spectacular mockup but inert interface -> every action has state transition.

N03. METAL PANEL INTERFACE (TYPE-SAFE DESIGN DATA)
  type FlatSide = 'top' | 'right' | 'bottom' | 'left';
  type PanelDepth = 'flat' | 'small' | 'medium' | 'shell';
  type ShapeFamily = 'cut-tr'|'cut-bl'|'tongue'|'receptor'|'tiered'|'rail-socket'|'boot'|'plate'|'canopy'|'well'|'hinge';
  type Accent = 'neutral'|'orange'|'cyan'|'violet'|'teal'|'red';
  interface MetalPanelProps {

N04. SVG SILHOUETTE / PATH RECIPE
For variable viewport dimensions W,H and cut C, build polygon points in order rather than raster image:
  Example canopy (flat bottom, 3D other sides):
    P0=(C,0), P1=(W-2*C,0), P2=(W,C), P3=(W,H-C),
    P4=(W-C,H), P5=(0,H), P6=(0,C).
    Trace M P0 L P1 ... Z; round only purposeful material corners.
  Outer face = path at z=0; extruded side faces = pair each non-flat edge with its offset at d=(+8,+7); skip bottom edge when flatSide='bottom'. Use per-edge gradient varying by normal direction. Inner inset contour must be a true offset or separately authored path; scaling whole SVG about its center is not a reliable fixed-width bevel.
  For more complex notches: compose edges as a sequence of segments, and keep shared docking points exactly equal between neighbors. Reserve inset areas for controls and texture.

N06. EDGE/FACE MATERIAL CONSTRUCTION
Layer order (back→front): global shadow → smoke/particle emitter → outer chassis side faces → rear structural web → main surface polygon → inner bevel → vents/screws → content window → interaction focus border. Only on active surface: emissive seam at connector or side channel and minor bloom. Text z-index above everything. For performance, cache SVG paths per shape+size; resize observer only updates when bounds change materially, avoid continuous path regeneration on scroll.

N07. SPRAY CLOUD CODE BEHAVIOR
Input {seed, anchor, hue, radius, density, energy, clipRegion, motionEnabled}. Generate deterministic noise and particles; cloud origin comes from vent/LED location. Use small particles, irregular opacity falloff, and coarse wisps; mask away from text safe zones. For static HTML, use pseudo-element with multiple radial gradients + noise image stored locally as data URI if needed; no external network dependency. In app, `prefers-reduced-motion` disables drift; inactive route can pause rendering via IntersectionObserver; hover shouldn't mount hundreds of expensive DOM nodes.

N08. TREEMAP ALGORITHM
Input hierarchical files with verified byte size. Exclude unknown-size nodes from area allocation and report coverage separately. Compute local parent size using a consistent bytes-counting policy; choose squarified treemap to minimize extreme aspect ratios. Sort by size descending or stable saved order, consistent between rerenders; each tile area = nodeSize/sumKnownSizes * availableArea (minus gutters), respecting a minimum clickable visual threshold. Aggregate very small nodes under 'Other (n)' with subtotal, drill into that group; do not enlarge small tiles arbitrarily without explaining distortion. Account for the panel outline safe rect: all actual tiles stay inside a rectangular work well even if outer shell is chamfered. Determine bounds on ResizeObserver and avoid synchronous layout thrashing. On selection highlight tile and inspector, maintain stable breadcrumbs.

N09. UNIVERSAL CHART RENDER STRATEGY
Prefer SVG for small to medium data, Canvas for >few thousand marks or frequent streaming, WebGL only for high-volume plots/3D models when justified. Chart data pipeline must be independent of visual renderer: normalize verified units, validate source, aggregate, derive domains, choose ticks, render, expose accessible data table. Never let opacity gradients imply additional observations. Keep data decimation bounded/transparent. Tests assert representative exact values and no invented samples.

N10. SCANNER BRIDGE TYPE CONTRACT
  type DataState<T> =
    | {kind:'unknown'}
    | {kind:'loading'; requestId:string}
    | {kind:'partial'; data:T; coverage?:number; sampledAt:string}
    | {kind:'ready'; data:T; sampledAt:string; source:string}
    | {kind:'stale'; data:T; sampledAt:string; reason:string}
    | {kind:'error'; code:string; message:string; retryable:boolean}
    | {kind:'permission-denied'; scope:string; remediation?:string};
  interface ScannerBridge {
    getVolumes():Promise<DataState<Volume[]>>;
    scan(scope:ScanScope, signal?:AbortSignal):AsyncIterable<ScanEvent>;
    getChildren(folderId:string):Promise<DataState<FileNode[]>>;
    getFileDetail(fileId:string):Promise<DataState<FileDetail>>;
    openInFinder?(fileId:string):Promise<void>;
  }
Mock/demonstration data MUST be labeled and isolated from production bridge; never silently fall back to invented data on API errors.

N11. NOTIFICATION BRIDGE TYPE CONTRACT
  interface NotificationPrefs {osAuthorized:boolean; scanCompleted:boolean; storageThreshold:boolean; errors:boolean; quietHours?:TimeRange}
  interface NotificationEvent {id:string; category:string; severity:string; title:string; body?:string; deepLink?:string; privacy:'public'|'private'; occurredAt:string}
  interface NotificationBridge {
    getOSPermission():Promise<'authorized'|'denied'|'not-determined'|'unavailable'>;
    requestOSPermission():Promise<boolean>;
    showOSNotification(event:NotificationEvent):Promise<'shown'|'suppressed'|'failed'>;
    saveInAppNotification(event:NotificationEvent):Promise<void>;
  }
Protect private file paths before constructing OS notification, avoid duplicate event ids, route to app when opened. OS notifications not implementable by CSS/HTML alone in offline file contexts.

N12. OVERLAY MANAGER
Use a single portal root outside transformed/clipped panel ancestors. Stack order: popover/menu < toast < dialog/confirm < system-owned OS alert (outside DOM). Menus pinned by anchor rect, collision-detected. Focus trap only for modal surfaces. Scroll locking only on modal. On route change close transient overlays and preserve durable notification inbox. Avoid universal z-index:999999; use levels.

N13. CONTENT SECURITY
Filesystem filename/path is untrusted user-controlled text: render as text nodes, not innerHTML. Escaping mandatory for reports/previews. Dangerous file operations require exact path/ID and OS permission; never rely solely on front-end state. When file counts and sizes reflect only current directory, do not call them whole-disk totals. Browser demo must not claim access to local filesystem without user selection or native bridge. Avoid leaking filenames in analytics, telemetry or cloud model prompts without explicit opt-in.

N14. PERFORMANCE BUDGETS
Target 60fps on ordinary navigation/scroll, or better than incumbent under measured conditions. Table render bounded by viewport + overscan ~8–15 rows where row height permits. Memoize normalized file tree, avoid sorting every render; batch event updates. Pause offscreen particles, avoid shadow animations causing repaint across whole viewport. Limit backdrop-filter layers; use reduced graphics tier for Intel Macs and battery power. Measure input-to-paint, scroll jank, memory, DOM nodes, chart data points, idle CPU, and long tasks. Use CSS `content-visibility` thoughtfully but validate measurement and focus behavior.

N15. TESTS REQUIRED BEFORE COMPLETION
  Unit: number formats, dedupe logic, source coverage, unknown states, shape path bounds, geometry safe insets.
  Integration: sidebar route, search scope, scan events, progress job, inspector selection, notification routing, OS permission denial.
  Accessibility: keyboard Tab, focus order, semantic labels, screen reader table, reduced motion and high contrast.
  Visual: 320/375/600/820/1024/1440/1920 widths, compact window, browser zoom 125/150/200%.
  Behavior: 100k rows, 10k tree nodes, 50k chart points, stale data, partial data, slow requests, cancel, error, empty, long strings.
  Safety: delete preview/confirmation, per-item failure rollback, privacy/no path leak, OS notification consent.
  Performance: record before/after frame timing and memory; no 'faster' claim without benchmark.

O03. DESIGN REVIEW RUBRIC (SCORE 0–5 EACH)
A Geometry: custom shape grammar, interlocking shared anchors, one genuine flat edge, 3 actual depth faces.
B Hierarchy: user knows current context/action in 2 seconds, task in 10 seconds.
C Fidelity: panel positions/seams/proportions meet supplied reference; not a generic dashboard.

K Feedback: progress, errors, notifications properly scoped and routed.
L Product safety: privacy, permission, deletion, undo semantics valid.
Passing target: total >=51/60 and NO score below 3; critical blockers: D/E/H/L <4 must fix before ship. A beautiful but fake shell fails.

O04. SELF-CRITIQUE / ITERATION LOOP
After every design pass ask:
  - Are the shapes genuinely part of the layout or just borders around rectangles?
  - Which 3 edges show depth? Is the 4th edge actually planar?
  - Can every label, chart and button fit inside safe rectangle without occlusion?
  - Does smoke start from mechanical vents/corners, not behind important text?
  - Are repeated panels derived from one shape family with deliberate exceptions?
  - Would a user understand navigation without neon or 3D effects?
  - Are axes/tables more readable than before redesign?
  - Is current status truthful for an unscanned installation?
  - What happens for a failed action, no data, denied access and stale scan?
  - Can keyboard users complete the task without hover?
  - Will this remain smooth on an older Intel Mac with thousands of files?
If any answer fails, adjust layout and behavior before adding more decoration.
